# 塑形复杂开发任务

在修改代码前发现并关闭会改变产品结果、系统结构或交付风险的关键问题。将任务契约落盘为后续实现和验收的事实来源；不要依赖对话历史保存结论。

## 核心规则

- 在塑形完成并获得用户明确确认前，不要修改实现代码、接口、数据库结构或运行环境。
- 每个面向用户的回合最多提出一个需要决策的问题。不要用编号、并列句或多个问号隐藏子问题。
- 当前问题未形成明确结论前，留在当前分支深入讨论；关闭后再返回问题队列。
- 能从代码、文档、配置、测试、日志或运行状态查证的事实必须自行查证，不要询问用户。
- 只向用户询问意图、语义、取舍、优先级，以及静态事实无法决定的问题。
- 同时定义产品行为契约和工程架构契约。不要用架构清单替代产品目标，也不要让产品目标掩盖系统约束。
- 让审查深度与风险相称。简单且明确的工作不要被扩张成完整设计项目。
- 保持任务范围稳定。主动架构建设、契约变化和高代价重构必须说明收益与代价并获得确认。

## 1. 判断是否进入塑形

根据整体意图判断，不匹配固定关键词。仅当用户表现出准备启动一项复杂开发工作的明确倾向，并且任务仍存在显著的行为、范围、架构或验收决策时进入本流程。

以下情况不要触发：

- 用户仍在探索问题空间，没有准备进入开发；
- 修改局部、目标明确、风险低且验收直接；
- 用户只要求解释、诊断、查询或执行简单命令；
- 已存在经过确认、足以指导实现的任务契约。

若同一任务已有塑形文档，继续更新该文档，不要新建重复文件。

## 2. 查证现状并初始化文档

在提问前先读取任务相关事实：

1. 读取适用的 `AGENTS.md`、`CONTEXT.md`、ADR、架构文档和开发规范。
2. 定位相关入口、调用链、数据所有权、接口、配置、测试和实际消费者。
3. 区分已经查证的事实、用户已确认的决策、Agent 建议、待确认问题和明确非目标。
4. 查找仓库已有的开发任务文档目录和格式；存在规范时遵循原规范。
5. 没有现有规范时，从 [任务契约模板](assets/development-task-contract.md) 创建 `docs/dev/YYYY-MM-DD-<task-slug>.md`。
6. 创建后立即写入已知事实和证据，并在每个决策关闭后同步更新。不要自动提交 Git。

初始文档是带有未知项的框架，不是伪装成完整方案的猜测。不要为了填满章节而补写未经验证的结论。

## 3. 建立决策队列

从目标、行为状态空间、系统影响和验收方式中识别待决策项，并写入文档。按以下顺序选择当前问题：

1. 会改变大量后续结论的上游问题；
2. 产品语义、成功标准和范围边界；
3. 不可逆、兼容性敏感或修正代价高的问题；
4. 架构责任、数据边界和失败语义；
5. 局部实现偏好。

问题队列可以有多个条目，但对话中始终只有一个“当前问题”。

## 4. 执行单问题决策循环

每次提问包含必要的决策上下文，但只请求一个结论：

1. 说明为什么现在需要决定；
2. 给出已经查证且与问题直接相关的事实；
3. 必要时列出互斥选项及主要代价；
4. 有充分依据时给出明确建议；
5. 提出一个可直接回答的问题。

若用户的回答引出更深层分支，将新分支归入当前问题，暂停其他问题。讨论形成结论后：

1. 用直接语言复述结论及主要影响；
2. 确认用户认可该结论；
3. 更新任务文档中的相应章节和决策记录；
4. 标记当前问题关闭，并记录新发现的问题；
5. 回到暂停的位置，选择下一个问题。

不要重复询问已关闭的问题，除非新的系统事实使原决策失效。若用户一次主动回答了多个问题，记录所有已明确内容，但下一次仍只选择一个未关闭问题。

## 5. 补全产品行为契约

将目标转换为“前置状态 + 动作 -> 可观察结果”。根据任务实际风险选择相关维度，不要机械展开全部项目：

- 使用者、权限和入口；
- 数据不存在、已存在、过期或部分完成；
- 新增、修改、删除、取消、重试和重复执行；
- 加载、处理中、刷新、重新登录或重启后的状态；
- 参数错误、依赖失败、超时和部分成功；
- 页面、接口、持久化、事件、文件及下游消费者的最终结果；
- 必须保持不变的现有行为和不变量。

为每个需求点指定验收证据。优先使用真实用户路径、真实消费者边界和可执行检查，不要只用实现内部断言证明产品结果。

## 6. 补全工程架构契约

读取 [架构审查维度](references/architecture-review-dimensions.md)，仅选择有事实依据且与本次变更相关的维度。将架构内容分为：

- 现有架构不变量：从仓库和运行系统查证，默认必须保持；
- 本次变更引入的工程风险：由影响链推导出需要新增的约束；
- 主动架构建设：为了已知变化压力承担额外结构成本，必须由用户确认。

每个工程目标都要写清驱动力、约束、允许的代价和验收证据。拒绝单独使用“可维护”“可扩展”“高内聚”“更优雅”等无法证伪的目标。

## 7. 按任务类型调整重点

| 任务类型 | 优先补全内容 |
| --- | --- |
| 新功能 | 用户结果、行为状态空间、数据与接口契约、端到端验收 |
| 复杂缺陷 | 真实事实链、根因、失败语义、修复边界、回归保护 |
| 重构 | 必须保持的不变量、迁移步骤、兼容窗口、回滚和等价性证据 |
| 性能优化 | 基线、目标数值、负载模型、资源代价和回归阈值 |
| 基础设施 | 环境边界、依赖、权限、可观测性、发布顺序和回滚演练 |

## 8. 进行完整性复查

当高优先级问题全部关闭后，重新读取最新任务文档和相关系统事实：

1. 检查每个需求是否都有条件、动作和可观察结果；
2. 检查每个架构目标是否有事实驱动力和验收证据；
3. 检查需求点、风险和验收项是否一一对应；
4. 检查范围外内容和必须保持的行为是否明确；
5. 列出三个最可能出现的“代码看似完成，但实际体验不符合目标”的情况，并确认验收已覆盖；
6. 检查已确认决策之间是否出现冲突或新的上游问题。

发现实质缺口时，将其加入队列并继续单问题循环。不要声称需求绝对完备；判断它是否已经足以安全进入实现。

## 9. 判断就绪并交接

仅在以下条件全部满足时将文档状态改为“就绪”：

- 用户目标和成功标准清晰；
- 相关产品行为可以被客观验收；
- 系统影响、架构不变量和主动架构投入已经区分；
- 范围、非目标、主要风险和失败处理明确；
- 高影响问题已关闭，剩余未知项不会改变外部行为、接口契约、核心结构或交付成本；
- 每个关键目标都有对应验收证据。

文档就绪后，简要说明就绪依据，并只提出一个交接问题：是否进入实现阶段？

未经用户明确确认，不要修改实现代码。获得确认后，以落盘任务契约作为实现和验收的事实来源；实施中发现契约缺口时，先更新问题队列并重新对齐，不要静默选择产品语义或扩大范围。
