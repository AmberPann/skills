# 塑形复杂开发任务

在修改代码前发现并关闭会改变产品结果、系统结构或交付风险的关键问题。将任务契约落盘为后续实现和验收的事实来源；不要依赖对话历史保存结论。

## 核心规则

- 在塑形完成并获得用户明确确认前，不要修改实现代码、接口、数据库结构或运行环境。
- 能从代码、文档、配置、测试、日志或运行状态查证的事实必须自行查证，不要询问用户。
- 只有当待定事项会实质影响产品行为、范围、系统边界、风险或交付成本，且需要用户表达意图、作出取舍或授权时，才向用户提问。
- 自行查证并决定局部实现。对于需要根据运行时输入作出的判断，在设计中明确规则和约束，由系统在执行时处理。
- 同时定义产品行为契约和工程架构契约。不要用架构清单替代产品目标，也不要让产品目标掩盖系统约束。
- 让审查深度与风险相称。简单且明确的工作不要被扩张成完整设计项目。
- 保持任务范围稳定。主动架构建设、契约变化和高代价重构必须说明收益与代价并获得确认。

## 1. 判断是否进入塑形

根据整体意图判断，不匹配固定关键词。仅当用户表现出准备启动一项复杂开发工作的明确倾向，并且任务仍存在显著的行为、范围、架构或验收决策时进入本流程。

以下情况不要触发：

- 用户仍在探索问题空间，没有准备进入开发；
- 修改局部、目标明确、风险低且验收直接；
- 用户只要求解释、诊断、查询或执行简单命令；
- 已存在经过确认、足以指导实现的任务契约。

若同一任务已有塑形文档，继续更新该文档，不要新建重复文件。

## 2. 查证现状并初始化文档

在提问前先读取任务相关事实：

1. 读取适用的 `AGENTS.md`、`CONTEXT.md`、ADR、架构文档和开发规范。
2. 定位相关入口、调用链、数据所有权、接口、配置、测试和实际消费者。
3. 区分已经查证的事实、用户已确认的决策、Agent 建议、待确认问题和明确非目标。
4. 查找仓库已有的开发任务文档目录和格式；存在规范时遵循原规范。
5. 没有现有规范时，从 [任务契约模板](assets/development-task-contract.md) 创建 `docs/dev/YYYY-MM-DD-<task-slug>.md`。
6. 创建后立即写入已知事实和证据，并在每个决策关闭后同步更新。不要自动提交 Git。

初始文档是带有未知项的框架，不是伪装成完整方案的猜测。不要为了填满章节而补写未经验证的结论。

设计讨论、文档和实现沿用项目已有的术语与定义。只有确有必要区分新概念或消除歧义时，才新增或改名，并记录定义和理由。

## 3. 建立决策队列

根据已知目标、系统事实和约束，先形成尽可能完整的设计建议。按核心规则筛选仍需用户决定的事项，写入待确认队列。队列可以为空。优先处理会改变后续设计的事项。

1. 会改变大量后续结论的上游问题；
2. 产品语义、成功标准和范围边界；
3. 不可逆、兼容性敏感或修正代价高的问题；
4. 架构责任、数据边界和失败语义；

## 4. 组织提问并记录决策

只询问确实需要用户判断的事项。能基于同一组背景一起决定的问题，可以集中提出，并给出建议和关键影响。如果一个答案会改变其他问题是否成立、有哪些选项或如何取舍，先问这个上游问题。用户已明确回答的事项直接记录，有实质歧义时再追问。

用已经查证的事实说明为什么现在需要决定，并在结论明确后更新任务文档和决策队列。新的事实或约束实质改变原有取舍时，重新打开对应决定。

## 5. 定义可观察的产品行为

把产品目标写成行为规则。每条规则说明三个要素：

- **条件**。什么事实会影响结果，例如调用者的权限、数据是否存在、任务当前的状态。
- **动作或事件**。什么触发了这条规则，例如用户提交请求、执行端报告完成或等待超时。
- **可观察结果**。用户或调用方能看到什么，例如返回结果、任务状态变化或生成的文件。

先写正常情况下的行为，再补充会改变结果的分支。例如，任务已完成时收到取消请求，系统返回「任务已完成」。最后检查本次改动涉及哪些既有行为，并记录必须继续成立的规则。

将这些规则写入任务契约，作为系统设计的输入。系统设计完成后，再选取真实用户路径并制定验收方案。

## 6. 设计系统如何实现产品行为

根据已明确的产品行为和查证过的系统现状，设计本次改动涉及的部分。写清楚三件事：

- **职责与状态归属**。哪些组件参与，各自负责什么，关键数据和状态由谁维护。
- **组件之间的交互**。请求、事件和结果如何传递，涉及哪些接口，调用方可以依赖什么行为。
- **约束与失败处理**。哪些已有约束必须继续成立，新增约束在哪里落实。发生超时、并发冲突或部分失败时，由哪个组件负责处理和恢复。

优先复用现有组件和接口。需要新增组件、改变接口或调整职责时，说明现有设计哪里无法满足要求，以及改动的影响和代价。将这次改动相关的设计决定写入任务契约。

参考 [架构审查维度](references/architecture-review-dimensions.md) 核对与本次改动有关的设计问题。

## 7. 按任务类型调整重点

| 任务类型 | 优先补全内容 |
| --- | --- |
| 新功能 | 用户结果、行为状态空间、数据与接口契约、端到端验收 |
| 复杂缺陷 | 真实事实链、根因、失败语义、修复边界、回归保护 |
| 重构 | 必须保持的不变量、迁移步骤、兼容窗口、回滚和等价性证据 |
| 性能优化 | 基线、目标数值、负载模型、资源代价和回归阈值 |
| 基础设施 | 环境边界、依赖、权限、可观测性、发布顺序和回滚演练 |

## 8. 在系统设计完成后制定验收方案

先完成产品行为和系统设计，明确范围、组件职责、接口、约束及关键失败处理，再选取并编排真实用户路径。**真实用户路径只用于测试验收。**

为每个关键需求、工程约束和失败场景指定可核对的证据。产品验收优先通过真实消费者边界观察结果，工程验收按需要使用接口检查、故障测试和回归测试。

如果验收发现缺口，先明确哪条通用需求或约束尚未满足，再据此修订设计，并用其他场景复验。

## 9. 进行完整性复查

当高优先级问题全部关闭后，重新读取最新任务文档和相关系统事实：

1. 检查每个需求是否都有条件、动作和可观察结果；
2. 检查每个架构目标是否有事实驱动力和验收证据；
3. 检查需求点、风险和验收项是否一一对应；
4. 检查范围外内容和必须保持的行为是否明确；
5. 列出三个最可能出现的“代码看似完成，但实际体验不符合目标”的情况，并确认验收已覆盖；
6. 检查已确认决策之间是否出现冲突或新的上游问题。

发现实质缺口时，先补充事实或修订建议。涉及用户意图、取舍或授权时，按第 3、4 节处理。判断现有契约是否已足以安全进入实现。

## 10. 判断就绪并交接

仅在以下条件全部满足时将文档状态改为“就绪”：

- 用户目标和成功标准清晰；
- 相关产品行为可以被客观验收；
- 系统影响、架构不变量和主动架构投入已经区分；
- 范围、非目标、主要风险和失败处理明确；
- 高影响问题已关闭，剩余未知项不会改变外部行为、接口契约、核心结构或交付成本；
- 每个关键目标都有对应验收证据。

文档就绪后，简要说明就绪依据，并请用户确认是否进入实现阶段。

获得用户明确确认后，以落盘任务契约作为实现和验收的事实来源。实施中发现契约缺口时，按第 3、4 节处理。涉及产品语义或范围变化时，与用户对齐后再执行。
