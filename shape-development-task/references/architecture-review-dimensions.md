# 架构审查维度

只读取和使用与当前任务有关的维度。每个维度都需要现有事实或本次变更风险作为触发依据；没有依据时标记为不适用，不要制造架构工作。

## 目标分类

### 现有架构不变量

从 `AGENTS.md`、ADR、架构文档、接口定义、代码依赖和运行拓扑中查证。记录定义位置、当前事实以及本次如何保持。

### 本次变更引入的工程风险

从新增或改变的数据流、调用链、状态转换和失败路径中推导。约束只覆盖实际风险，不扩张为通用平台建设。

### 主动架构建设

仅在存在已知变化压力、当前结构会持续产生可量化成本，并且本次投入明显降低长期总代价时提出。写清一次性成本、受益范围、放弃方案和退出条件，获得用户确认后再纳入范围。

## 审查维度

| 维度 | 需要查证的问题 | 可形成的工程约束 | 典型验收证据 |
| --- | --- | --- | --- |
| 责任边界 | 业务规则、编排、协议转换分别由谁拥有 | 规则只能进入明确的所有者模块 | 依赖检查、模块测试、调用链审查 |
| 依赖方向 | 新调用是否穿透层次或形成循环 | 保持既有依赖方向，公共层不反向依赖业务层 | 构建、依赖图、静态检查 |
| 数据所有权 | 谁创建、修改和解释状态 | 单一写入所有者，跨服务通过明确契约访问 | Repository/服务边界测试、数据流审查 |
| 一致性与事务 | 哪些写入必须原子完成 | 明确事务边界、补偿策略和部分成功语义 | 故障注入、事务测试、状态核对 |
| 接口兼容 | 哪些调用者依赖字段、错误或时序 | 保持兼容或定义迁移窗口和版本策略 | 契约测试、旧客户端回归、生成物检查 |
| 并发与幂等 | 请求是否会重复、乱序或并发执行 | 定义幂等键、冲突规则和重试边界 | 并发测试、重复调用测试 |
| 失败与恢复 | 超时、依赖失败、进程重启后状态如何 | 明确失败状态、重试责任、恢复和人工介入路径 | 故障测试、重启测试、恢复演练 |
| 安全与权限 | 身份、租户和敏感数据如何传播 | 权限校验位于正确边界，不扩大数据暴露 | 权限矩阵测试、审计记录、负向用例 |
| 性能与容量 | 延迟、吞吐、内存、存储或成本是否改变 | 给出基线、目标数值、负载模型和资源预算 | 基准测试、压测、运行指标 |
| 可观测性 | 失败能否关联到任务、请求和关键状态 | 记录足以定位问题的指标、日志和追踪字段 | 日志样例、告警验证、链路查询 |
| 发布与回滚 | 是否涉及数据迁移、双写、配置或多服务顺序 | 定义兼容发布顺序、回滚条件和不可逆点 | 预演、迁移校验、回滚演练 |
| 测试边界 | 真实消费者在哪里读取结果 | 在实际契约和消费者边界验证，不只测试内部实现 | 路由级、契约级或端到端测试 |
| 可演进性 | 已知后续变化会修改哪些稳定边界 | 只为已证实的变化点保留扩展空间 | 后续场景适配分析、删除重复分支 |

## 按任务类型选择重点

- 新功能：责任边界、数据所有权、接口兼容、一致性、权限、测试边界。
- 复杂缺陷：失败与恢复、并发与幂等、真实消费者、可观测性、回归不变量。
- 重构：依赖方向、接口兼容、发布与回滚、等价性测试、删除旧路径的条件。
- 性能优化：性能基线、负载模型、资源预算、热点证据、正确性回归。
- 基础设施：运行拓扑、权限、容量、可观测性、发布顺序、回滚和灾难恢复。

## 拒绝不可验收的表述

不要单独记录以下目标：

- 提高可维护性；
- 增强扩展性；
- 让架构更优雅；
- 降低耦合；
- 提高稳定性。

将它们改写成可证伪的契约。例如：

```text
驱动力：同一业务规则目前在三个入口重复，并且已经发生行为不一致。
工程约束：规则由一个领域模块拥有，三个入口仅负责参数转换。
允许代价：本次迁移三个入口，不建设通用规则框架。
验收证据：三个入口运行同一组契约用例，旧重复实现被删除。
```

## 架构目标的停止条件

若一个目标无法回答以下任一问题，不要纳入任务：

1. 当前有什么事实或变化压力要求它？
2. 不做会产生什么具体成本或风险？
3. 本次需要增加什么约束或结构？
4. 如何客观证明目标已经达到？
5. 它是否改变本次范围、交付时间或回滚代价？
