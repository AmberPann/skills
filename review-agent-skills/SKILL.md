# Agent Skill 审查

审查 Skill 时，把它视为 Agent 阅读的说明书。执行者是 Agent；Skill 本身不调用工具、不维护状态，也不产生结果。

审查目标是判断这份说明书是否值得存在、能否在目标 Agent 系统中奏效，以及内容是否按阅读目的合理组织。不要因为格式合法、平台验证通过或规则写得详细，就认定 Skill 有效。

默认只读审查。除非用户明确要求修改，否则不要编辑被审查的 Skill、平台 Workspace 或运行配置。

首次向用户展示完整审查结果前，读取 [交互约定](references/interaction-contract.md)。在 Codex 中运行且当前环境提供 `visualize` 时，再读取 [Codex UI 适配器](references/codex-ui.md) 和当前 `visualize` Skill；其他环境使用 Markdown 回退，不猜测平台能力。

## 先确定目标 Agent

开始审查前，先确定这份 Skill 供哪个 Agent 和运行环境使用。优先从用户说明、Skill package、仓库、运行配置和文档中查证；现有证据无法唯一确定时，停止审查并询问用户。

对自建 Agent，要求用户提供代码仓库或相关文档，至少能够查明 Skill 的发现与加载方式、可用工具及 schema、上下文与持久化能力、权限和用户交互边界。目标 Agent 或关键运行边界未确定时，不得把审查标记为完整。

在审查状态中记录目标 Agent、运行环境和证据来源。所有结论只适用于已记录的对象和边界。

## 基本概念

### 阅读目的

阅读目的，是 Agent 在可识别的情境下阅读一组内容后要解决的具体问题，例如做出判断、选择路径、执行受约束的操作或理解稳定 contract。

内容围绕同一业务主题，只能说明它们相关。只有这些内容在相同情境下共同服务于一个具体问题，才构成放在同一阅读单元的依据。

### 阅读单元

阅读单元是 Agent 为完成一个主要阅读目的而需要一起阅读的内容。它通常是一个文件，也可以是因物理长度而拆开的、始终共同读取的一组文件。

条件分支不属于主流程的强制阅读单元。只有触发条件成立时，才读取对应 reference。

阅读单元不一定拥有完整生命周期。被动的领域知识、判断标准或策略 reference 可以只帮助 Agent 解决一个局部问题；读取条件、结果消费和后续流程可以由调用它的 `SKILL.md` 统一负责。只有阅读单元自身包含状态转换、工具调用、用户交互、等待、持久化或外部副作用时，才需要独立说明完成、停止、失败和恢复条件。

### 高内聚

一个阅读单元高内聚，意味着：

- 只有一个主要阅读目的；
- 各段内容直接影响同一个具体问题；
- 各段通常在相同情境下被需要；
- 删除关键部分后，Agent 无法正确解决该问题；
- 不夹带可以独立成立的另一类工作；
- 内容通常因同一个原因一起变化。

不要通过扩大 description 或标题让无关内容显得相关。应从真实使用情境和因果关系判断。

### 低耦合

两个阅读单元低耦合，意味着：

- A 能独立说明为什么需要阅读、适用于什么情况，以及如何完成自己的阅读目的；
- A 能独立判断何时需要继续读取 B；
- A 不复制 B 的规则，也不依赖 B 的内部章节和实现细节；
- B 的内部变化通常不要求修改 A；
- 依赖方向明确，不形成循环；
- B 不可用时，A 说明应停止、改走其他路径还是询问用户。

低耦合不要求完全没有依赖。合理依赖是通过明确的读取条件、稳定 contract 或系统接口连接。

## 审查前先还原 Skill 的脉络

第一次讲解一个 Skill 时，先回答以下问题，再进入问题列表。

### 它解决什么问题

说明：

- Agent 在什么具体情境下需要这份说明；
- 没有它时，Agent 会在哪个可复核场景做错；
- 错误表现是过早行动、遗漏判断、错误承诺、错误选材、越权操作，还是无法停止。

不要用“提升质量”“规范流程”一类抽象描述代替具体失败场景。

### 何时启用、继续或跳过

分别检查 Skill 和 references 的适用条件：

- `description` 使用哪些可观察的用户意图、输入或任务状态触发 Skill；
- 主文依据哪些事实继续、停止或转交；
- 主文中的哪个条件分支要求读取或跳过 reference；
- Agent 能否在作出选择前观察到这些事实，并定位其来源。

`description` 负责初步触发，主文负责复核范围、停止和转交。只写“处理某类任务时使用”不能形成可执行边界。

### 它如何解决问题

用 Agent 的行为描述解决机制：

- Agent 需要识别哪些事实；
- 需要做哪些判断或采取哪些行动；
- 何时读取条件 reference；
- 何时需要用户参与；
- 何时停止当前说明并转入另一份说明；
- 需要保留哪些信息供后续阶段读取。

不要把 Skill 写成会思考、调用工具或生成文件的主体。

### 文章如何组织

按阅读目的说明每个章节的作用，并判断顺序是否符合读者需要：

1. 先建立问题、适用范围和边界；
2. 再给核心解决路径；
3. 在对应分支附近链接条件 references；
4. 最后给交接、停止和异常边界。

如果入口判断之前先出现工具细节、错误清单或低频例外，应检查是否需要重排。

## 建立证据

静态可查的内容必须查证，至少覆盖：

- 完整 `SKILL.md` 和实际会触发的 references；
- Skill 引用的真实 tool schema 与运行时可用状态；
- 被点名的其他 Skills 是否存在并在目标环境有效；
- Skill 定义的记录是否有明确的写入方式、消费者和失效规则，但消费者不要求必须在本 Skill 内定义，只要客观逻辑上可能存在即可；
- 用户被要求执行的确认、授权或上传动作是否真实可操作；
- 确定性要求是否有 parser、validator、权限或持久化机制支持。

区分以下证据：

- 文档声明；
- 当前代码和 schema；
- 目标环境的运行时配置；
- 实际工具调用或日志；
- 仍未执行的推断。

平台静态验证通过，只能证明平台规则允许该包，不能证明说明中的工作机制可执行。

## 引导式审查流程

完整 Skill 或 package 审查默认使用引导式流程。用户只问一个局部问题，或目标确实很小且四个维度能在一份紧凑回复中讲清时，直接给精简完整审查，不强行展示地图。

### 先完成一次全量分析

展示地图前，完成本次范围内的全部分析：还原 Skill 脉络，读取主文和实际触发的 references，核对所需证据，填写四个维度的覆盖记录，形成问题说明、findings、总体结论和未确认项。章节是同一份分析的不同视图，不能等用户点击后才开始审查该维度。

读取 [审查状态](references/review-state.md)，按其结构准备完整草稿并保存：

```bash
python3 <skill-dir>/scripts/review_state.py save --input <draft-json>
```

目标 Agent 或其证据未记录、`analysisStatus` 不是 `complete`、四个维度不完整、阅读单元未覆盖、问题没有关联覆盖项，或源文件指纹无效时，不得展示地图。

### 用四个审查维度组织地图

地图固定包含四章，顺序如下：

1. 可行性；
2. 内容必要性、增量和信息密度；
3. 内容清晰度；
4. 术语与指代。

每章显示一句话目的、覆盖状态数量、findings 数量和一个详评入口。地图同时提供“只看问题”和“完整审查”。首次展示只给 Skill 脉络、范围、证据边界和地图，不展开四章正文。

需要推荐入口时，说明具体理由，例如该维度包含唯一 P1、是其他判断依赖的前置边界，或最贴近用户当前问题。没有证据支持顺序时，四章保持同等权重。

### 从同一状态展示详评

用户选择维度、只看问题、完整审查或返回地图时，先加载并校验状态：

```bash
python3 <skill-dir>/scripts/review_state.py load --state <statePath>
```

源文件已变化或状态校验失败时，停止使用旧结论，说明状态已经失效，再重新分析。状态有效时只切换视图；不要重新读取全部文件、重复审查或重复验证。只有用户提出新问题，或已记录的未确认项需要补充证据时，才更新完整状态。

维度详评必须展示该维度的完整覆盖记录。每条 `有问题` 除表格结论外，还要给一段精简、清楚的问题说明：指出问题是什么和准确位置，说明当前文本、schema 或运行边界如何引入问题，再说明可复核的触发条件、实际影响和处理方向。不要只写“存在风险”“内聚不足”或“建议优化”。具体格式见 [交互约定](references/interaction-contract.md)。

### 完成并清理

用户完成所需章节后，汇总已查看和未查看的维度、所有 findings、仍未确认项及证据边界。审查结束、用户提前停止或状态失效时，清理临时状态：

```bash
python3 <skill-dir>/scripts/review_state.py cleanup --state <statePath>
```


## 审查维度与覆盖记录

每次完整审查都建立覆盖记录，不能只展示 findings。覆盖记录使用以下固定列：

| 审查维度 | 检查问题 | 状态 | 具体结论 | 证据 / 关联 Finding |
|---|---|---|---|---|
| 可行性 | 系统是否提供本阅读单元要求的具体工具或能力？ | 通过 / 有问题 / 未覆盖 / 不适用 | 写明哪些能力满足或缺失，以及影响哪条路径 | 文件与行号、tool schema、运行配置，或 Finding 编号 |

`审查维度` 只能使用本节定义的四类：`可行性`、`内容必要性、增量和信息密度`、`内容清晰度`、`术语与指代`。拆分和放置判断归入 `内容必要性、增量和信息密度`，不要另造顶层维度。

每行只回答一个可独立判断的问题，并写明被检查的 Skill、reference、章节、记录或工具。不要把多项合并成“工具能力”“内容质量”“结构问题”一类总项。一个检查问题涉及多个对象，而这些对象的结论或证据不同时，拆成多行。

状态含义：

- `通过`：已经检查，证据足以证明当前要求成立；具体结论必须写出成立的对象和边界。
- `有问题`：已经检查，并发现具体缺陷；达到 P1、P2 或 P3 门槛时关联 Finding，未达到时仍保留审查结论。
- `未覆盖`：本次无法完成检查；写明缺少的文件、schema、运行状态或其他证据。
- `不适用`：触发条件在当前阅读单元中不存在；写明为什么不适用，不能用它代替未检查。

下列四个维度中的每个检查项都是基线问题。完整审查必须逐项进入覆盖记录；同一基线问题在不同工具、记录或阅读单元上结论不同时，分别记录。

### 可行性

逐项判断：

- 系统是否向 Agent 提供了说明要求的 action、tool、文件系统、上下文和环境能力；
- Agent 是否能观察到规则要求它判断的事实；
- tool output 是否真的包含说明要求记录的证据；
- 需要用户确认或授权时，用户是否看得到决策材料，并能执行该操作；
- 跨轮或长任务中，必要信息是否被可靠持久化，而非只依赖模型记忆或摘要；
- 当当前阅读单元拥有行为流程时，工作何时完成、停止、等待用户或转入另一份说明是否明确；
- 当当前阅读单元可能失败或产生副作用时，是否存在可执行的恢复路径；
- 确定性要求是否由系统保证，还是只要求模型自证。

以下情况通常构成实质问题：

- 要求调用不存在或未启用的工具；
- 要求读取 Agent 实际看不到的状态；
- 要求记录 tool output 没有返回的字段；
- 要求确定性解析、去重或校验，但没有对应机制；
- 要求用户确认，但用户没有看到被确认的对象；
- 定义了记录，却没有可靠方式选择当前有效 revision；
- 转交给不存在或无效的下游 Skill。

### 内容必要性、增量和信息密度

检查每一段是否真正改变 Agent 的判断或行动：

- 是否只是常识、口号或显而易见的工作要求；
- 是否重复其他 Skill 已经负责的内容；
- 是否复制 tool schema 的参数、枚举和限制；
- 是否在主文重复已要求读取的 reference；
- 是否用大量负向提醒反复表达同一个正向规则；
- 是否把低频边界放进每次必读的主流程；
- 是否定义了名称、文件或状态，却没有说明何时产生、谁会读取、何时失效；
- 是否为了单个历史失败累积了普遍规则，却没有稳定适用条件。

对每段做删除检验：删除后，Agent 的判断或行动会缺失或改变吗？如果不会，应删除、合并或移到按需 reference。

对多个文件做共读检验：

- 始终一起读取、一起变化的内容，考虑合并或视为同一阅读单元；
- 只在局部分支读取的内容，保留为 reference；
- 有独立阅读目的的内容，拆成 Skill；
- 只描述稳定数据结构的内容，拆成 contract。

删除检验可以合并相邻且服务于同一问题的段落，但覆盖记录必须指出具体文件或章节以及删除、合并、下沉或保留的结论。共读和拆分结论必须说明两个阅读单元分别回答什么问题，不能只写“内聚不足”或“建议拆分”。

### 内容清晰度

检查说明书是否始终以 Agent 为读者：

- 用“识别、判断、读取、调用、记录、停止”直接要求 Agent；
- 避免“本 Skill 会调用”“Generation 生成”“Brainstorm 决定”一类把说明书写成行动主体的表达；
- 先写正确主路径，再补充需要防止的错误；
- 一个术语只表达一个概念；
- 系统标识保留原名，普通叙述优先使用自然语言；
- 对不常见概念说明其用途，不只给名称；
- 章节顺序服务于首次阅读，而非按规则追加时间排列；
- examples 用来澄清判断分界，不重复正文。

负向提醒只有在错误选项确实容易出现、后果明确且正向规则不足以排除时才保留。多个禁令指向同一正确行为时，合并为一条正向要求和一个必要反例。

### 术语与指代

- 保留领域标准、项目稳定术语、schema 字段和 tool 名称，不为显得系统化另造同义词；
- 自定义概念只有在后续规则需要反复引用、且没有现成准确表达时才引入；
- 自定义概念首次出现时说明它代表什么、用于哪个判断、何时失效；
- 不用口号式阶段名替代真实状态转换，例如一个标题无法说明输入、输出或完成条件时，应改成直接行为；
- `this`、`it`、`current`、`active`、`latest`、`the plan` 等指代必须能唯一对应当前可观察对象；
- `Gate`、`Contract`、`Context`、`Manifest` 等名称必须指向可定位的章节、文件、schema 或系统接口；
- 不引用 Agent 无法定位的上位规则，例如未提供名称、路径或注入契约的“全局规范”；
- 阶段名可以标识职责范围，但不能写成调用工具、读写文件或维护状态的行动主体。

### 逐阅读单元覆盖

除四个维度的通用检查外，对范围内的 `SKILL.md` 和每份实际触发的 reference，至少确认：

- 它的主要阅读目的，以及没有它时会缺失的判断或行动；
- 何时读取、何时跳过，触发条件是否来自 Agent 可观察的事实；
- 解决问题依赖哪些输入，结果由主流程或哪个下游消费者使用；
- 是否包含工具调用、用户交互、等待、持久化、状态转换或外部副作用；若包含，完成、停止、失败和恢复条件是否明确；若不包含，生命周期检查标记为 `不适用` 并说明它是被动知识或策略；
- 它与其他阅读单元是否需要共读，适合留在主文、reference、独立 Skill、contract、tool schema、代码或 assets 中的哪一处。

这些结论按所属问题写入四个审查维度，不另建一张只写“高内聚 / 低耦合”的汇总表。多个阅读单元结论相同也不能只抽样；可以合并展示，但必须列全适用对象，并证明它们的阅读目的、触发条件和证据相同。

## 拆分依据

评估阅读单元时，需要评估其内部以及和外部的拆分是否正确。判断内容 A 和 B 是否需要拆开时，依次回答：

1. A 和 B 是否共同完成同一个主要阅读目的？
2. A 是否在正常场景下可以完全不需要 B？
3. B 是否可以脱离 A，被其他工作单独使用？
4. A 和 B 是否会因为不同原因分别变化？
5. B 是否引入新的用户交互、授权或外部副作用？
6. B 是否需要独立说明何时阅读、停止或转交？

据此处理：

- 始终共同完成同一个主要阅读目的，缺一不可：放在同一阅读单元；
- 属于同一个 Skill，但只在某个条件分支需要：拆成 reference；
- 能独立适用，或拥有独立判断和行为边界：拆成 Skill；
- 只定义数据结构和字段语义：放入 contract；
- 需要系统确定性保证：放入代码、validator 或 action；
- 已由工具完整表达：放入 tool schema，Skill 只保留选择依据和结果消费方式。

不要只按文件长度、目录、工具名或已有组织方式拆分。

## 放置规则

| 内容 | 合适位置 |
|---|---|
| 问题、具体失败场景、何时阅读/跳过、核心路径、导航、停止和转交边界 | `SKILL.md` |
| 只在特定条件下需要的复杂问题 | `references/*.md` |
| 可独立适用的另一类问题和行为要求 | 独立 Skill |
| 跨阶段稳定的数据语义、字段和兼容规则 | contract |
| 参数、枚举、数量限制和真实返回结构 | tool schema |
| 解析、校验、权限、持久化、幂等和 active revision 选择 | 工具、Skill 内脚本（如果有） |
| 多个 Skills 必须以完全相同语义理解的稳定事实 | 有明确维护方的共享 reference 文件 |
| 生成结果会直接复用的模板、图片或其他材料 | assets |

### 主文

`SKILL.md` 应足以让 Agent 独立判断：

- 为什么现在需要阅读；
- 是否适用；
- 当前要解决什么问题；
- 核心解决路径是什么；
- 何时读取哪个 reference；
- 何时停止、等待用户或转入其他 Skill。

主文不应成为所有知识的汇总，也不应只是一个无法独立判断的目录。

### Reference

每份 reference 应集中解决一个局部问题。调用它的 `SKILL.md` 与 reference 合在一起，应能说明：

- 何时读取；
- reference 帮助 Agent 解决什么问题；
- 解决问题依赖哪些可观察事实；
- 结果由主流程如何消费。

被动的知识或策略 reference 不必重复调用者已经清楚说明的触发条件、返回位置和完整生命周期。若 reference 自己引入工具调用、用户交互、状态转换、等待、持久化或外部副作用，则该 reference 必须说明对应的完成、停止、失败和恢复条件。

Reference 不应隐藏要求读者继续追踪多份未声明文件的前置条件。

### 共享 Reference

只有同时满足以下条件才适合共享：

- 多个 Skills 需要完全相同的语义；
- 内容具有稳定、单一的权威来源；
- 不包含某个 Skill 特有的步骤；
- 修改时可以识别全部受影响消费者；
- 各消费者不会给同一字段附加不同含义。

不要因为文字重复就共享。会因不同业务原因独立变化的内容，应分别维护或提取更稳定的底层 contract。

## 常见拆分示例

### 制作视频与分发视频

二者不应因“都与视频有关”放在同一个 Skill。制作说明回答如何得到符合要求的成片；分发说明回答如何使用已有成片和外部账号完成平台发布。两者可以独立适用，也会因不同原因变化，应拆成独立 Skills。

### Generation 与模型路由

模型路由只在已经确定需要生成时帮助选择合法工具路线。它没有独立的用户意图，可以作为 Generation 的条件 reference。Generation 主文负责说明何时读取它。

### Artifact Schema 与校验

Skill 可以解释为什么需要记录某些事实、后续阶段如何使用。字段结构放入 contract；duplicate-key rejection、schema validation 和 active revision 选择交给确定性机制。不要要求 Agent 仅靠重新阅读文本证明解析成功。

## 形成审查结论

先给脉络，再给覆盖记录和问题。每个 Skill 或阶段至少包含：

1. 解决的问题和没有它时的具体失败；
2. 何时阅读、何时跳过和不负责范围；
3. 解决思路；
4. 文章结构；
5. 按四个审查维度展开的完整覆盖记录；
6. 可行性，内容必要性、增量和信息密度，内容清晰度，术语与指代的总体结论；
7. 有证据支撑的 findings；
8. 已验证内容和仍未确认项。

只有同时满足以下条件，才能把审查标记为完整：

- 已列出本次审查范围内的主文、references、外部 Skills、工具和记录；
- 已确定目标 Agent 和运行环境，并记录证据来源与未确认边界；
- 四个审查维度都出现在覆盖记录中，各维度的基线问题均有状态；
- 范围内每个阅读单元都完成了阅读目的、触发与跳过、输入与结果消费、生命周期适用性以及拆分和放置判断；
- 每条 `有问题` 都有具体对象、触发条件、影响和证据，达到严重程度门槛的条目已形成 Finding；
- 每条 `未覆盖` 都说明缺少什么证据，每条 `不适用` 都说明为什么没有对应触发条件；
- findings 可以追溯到覆盖记录，覆盖记录中的通过项和非 Finding 问题没有被省略。

任一条件未满足时，把当前结果标为部分审查，并明确下一步还需覆盖什么。E2E 是证据方式，不是独立的审查维度；用户没有要求 E2E，不自动等于审查不完整。若某个具体判断只能通过 E2E 确认，则把该检查项标记为 `未覆盖`，写明缺少的证据，并在“已验证内容和仍未确认项”中说明验证边界。不要把验证范围与审查覆盖混为一谈。

Finding 必须包含：

- 严重程度；
- 文件和准确行号；
- 问题是什么；
- 当前文本、schema、依赖或运行边界如何引入问题；
- 可复核的触发场景；
- 实际影响；
- 应移动、删除、合并、拆分，还是补足系统能力。

严重程度建议：

- `P1`：当前默认或重要路径无法闭环，或只能伪造系统并未提供的状态和证据；
- `P2`：明确的边界错误、隐藏依赖、无效转交、过宽激活或重要能力不完整；
- `P3`：信息密度、重复、章节顺序、说明主体或维护成本问题。

只有理论担忧、没有具体触发场景时，放入审查重点或未确认项，不写成 finding。

## 审查纪律

- 不把格式验证通过当作内容正确；
- 不要求每个 Skill 或阅读单元都具有完整流程；知识型和策略型 Skill/reference 可以只解决一个局部问题，生命周期由拥有状态转换和副作用的调用者负责；
- 不为了减少文件数强行合并不同阅读目的；
- 不为了渐进加载把一个本应共同阅读的问题拆成多层跳转；
- 不用抽象的“高内聚、低耦合”直接下结论，必须说明具体阅读目的、依赖和失败方式；
- 不在审查中擅自修改、发布或重组 Skill。
