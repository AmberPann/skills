# Agent Skill 审查交互约定

本约定管理审查地图、维度详评、只看问题、完整审查和最终总结。所有视图读取同一份已校验状态，不因用户切换视图重新分析。

## 输出语言

用户明确指定的语言优先。否则使用用户有效消息的主要语言，忽略粘贴的 Skill、代码、URL 和工具输出。标题、覆盖状态、问题说明、findings 和导航使用同一种语言。

## 通用 Markdown 地图

Codex UI 不可用或适配失败一次时，使用以下地图：

```md
Agent Skill Review

# <Skill 或 package 名称>

范围：<环境、版本、主文与 references 数量>

## Skill 脉络

- 解决的问题：<具体情境和没有它时的失败>
- 阅读边界：<何时阅读、何时跳过、不负责什么>
- 解决机制：<Agent 识别、判断、调用、记录和转交的主路径>
- 文章组织：<主文和 references 如何分工>
- 证据边界：<已查证内容和未确认项>

## 审查地图

1. 可行性：<一句话目的>（通过 N｜有问题 N｜未覆盖 N｜不适用 N；P1/P2/P3 共 N）
2. 内容必要性、增量和信息密度：<一句话目的>（...）
3. 内容清晰度：<一句话目的>（...）
4. 术语与指代：<一句话目的>（...）

<有依据时：建议先看第 N 章：<具体理由>。>

请选择：可行性｜内容必要性、增量和信息密度｜内容清晰度｜术语与指代｜只看问题｜完整审查
```

首次地图不展开覆盖记录和问题正文。地图可以显示数量和最高严重程度，不能只显示 findings 而隐藏 `未覆盖`。

## 维度详评

维度详评按以下顺序展示：

```md
Agent Skill Review

## N/4 <审查维度>

<说明本维度判断什么、为什么影响 Agent 的实际行为。>

总体结论：<一段自足结论>

### 覆盖记录

| 审查维度 | 检查问题 | 状态 | 具体结论 | 证据 / 关联 Finding |
|---|---|---|---|---|
| <当前维度> | <一个具体问题> | <状态> | <自足结论> | <来源或 Finding id> |

### 问题说明

#### [P1/P2/P3 或“审查问题”] <短标题>

<精简说明段落>

证据：<相邻的文件链接、schema、运行配置或原文>

### 仍未确认

- <本维度的未覆盖项；没有则省略>

下一步：回到地图｜上一维度｜下一维度｜只看问题｜完整审查
```

覆盖记录必须包含该维度全部基线问题和适用对象。没有 findings 的维度仍展示通过、未覆盖和不适用项；没有问题时省略“问题说明”，不改成表扬。

## 问题说明

每条 `有问题` 都要有可独立阅读的说明。优先写成一个三到五句的自然段，不把表格结论扩写成六个机械标签：

1. 第一处写清问题是什么，并给出准确文件、行号、章节、tool schema 或运行配置位置。
2. 接着说明当前内容如何引入问题，即哪条规则、依赖、状态转换、缺失能力或放置方式造成失败。这里解释当前机制，不猜测历史动机。
3. 再写可复核的触发条件和实际影响。触发条件来自输入、状态、用户动作、调用顺序或阅读路径。
4. 最后给出处理方向：保留、删除、合并、拆分、移动，或补足工具、contract、validator、权限和持久化能力。

只写证据能够推出的内容。没有具体触发场景的担忧放入“审查重点”或“仍未确认”，不升级为 Finding。引文只保留推出结论所需的最小完整段落，并紧邻结论。

## 只看问题

从四个维度读取所有状态为 `有问题` 或 `未覆盖` 的覆盖项。先按 P1、P2、P3 排列 findings，再列没有达到 Finding 门槛的审查问题和高影响未覆盖项。每项保留位置、引入方式、触发条件、影响和处理方向，不重新扫描文件。

## 完整审查

按固定四维顺序一次性展示全部章节。顶部只出现一次 Skill 脉络和证据边界；每章保留总体结论、完整覆盖记录、精简问题说明和未确认项。不要为了“一次性”删掉通过项，也不要重复相同证据段落。

## 最终总结

总结用户实际查看的维度、尚未展开的维度、全部 findings、非 Finding 问题、未覆盖项和证据边界。只有四个维度的覆盖记录都已完成，才能把分析本身标记为完整；用户没有逐章点击，不会让已经完成的分析退回部分状态。
