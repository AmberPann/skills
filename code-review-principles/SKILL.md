# Code Review Principles

在做代码审查、实现审查、CR 准则讨论时使用本 skill。

CR 的目标是判断实现是否适合它的预期用途，而不是寻找形式上的代码味道。结论必须来自已验证的代码、接口契约、schema、配置、测试、日志、运行证据或权威文档。

## 审查姿态

从预期行为和生产约束出发。

- 静态可查的事实必须直接查证，包括源码、接口、schema、配置、测试和日志。
- 测试通过只是证据之一，不等同于实现正确。
- 区分生产路径与 mock、fake、本地专用路径、测试 helper。
- 优先提出有具体失败路径的问题，避免泛泛的猜测。
- 每次审查都要重新覆盖完整审查面，不只盯着上一轮已发现的问题。
- 复审修复时，同时检查修改是否破坏了全局其他方面，包括接口契约、权限边界、状态一致性、性能资源、依赖边界和测试覆盖。
- 审查代码有效性和变更必要性，确认新增逻辑解决了真实问题，并且没有为了不存在的历史状态保留复杂分支。
- 结合系统阶段判断问题价值，不为低风险设计债强行扩大改动范围。

## 证据规则

不要把未经验证的假设作为结论前提。

- 如果事实可以静态查证，先查证，再推理。
- 如果行为取决于运行时状态，说明已有证据和仍未确认的部分。
- 判断兼容性需求时，查证相关代码是否已经合入、发布、被外部调用方依赖，或已经产生需要迁移的数据。
- 测试通过后，要确认测试是否覆盖真实接口和关键生产实现。
- 审查修复时，要确认旧失败路径已经不可能发生，或已有回归测试覆盖。

## 严重程度

用严重程度表达影响和合入风险。

- **P1**：合入前必须修。包括数据丢失、安全绕过、权限错误、默认路径不可用、不可逆状态破坏、严重并发问题、生产大输入或高负载场景稳定失败等。
- **P2**：应尽快修，或在扩大 rollout 前修。包括边界行为错误、生产实现支持不完整、明确性能问题、阻碍扩展的依赖边界、失败路径清理缺失、重要测试缺口等。
- **P3**：可维护性或清晰度改进。包括命名、文件组织、重复逻辑、过宽抽象、轻微 Go/style 问题、非阻塞技术债等。

当问题只有理论风险、缺少具体失败路径时，倾向降低一级。当问题影响默认配置、共享基础设施、安全、持久化状态或关键隔离边界时，倾向提高一级。

## Go 代码基础规范

审查 Go 代码时，至少要参考 Go 官方 Code Review Comments 做基础规范检查。该页面定位为 Go 代码审查中常见评论的集合，并且是 Effective Go 的补充。

基础检查至少覆盖：

- `gofmt` 或 `goimports` 是否处理了格式和 import 分组。
- context 是否作为需要它的函数的第一个参数传递，是否避免把 request context 存进 struct。
- error 是否被处理、包装和返回，错误字符串是否符合 Go 习惯。
- goroutine 生命周期是否清楚，是否可能泄漏、阻塞或造成数据竞争。
- interface 是否定义在使用方，是否避免为了 mock 过早抽象。
- 命名是否符合 mixedCaps、initialisms、receiver name、package name 等习惯。
- exported declaration 是否有合适 doc comment，注释是否能服务 godoc。
- 函数边界、缩进错误流、裸 return、named result、empty slice、panic 使用等是否符合 Go 常见审查意见。

Go Code Review Comments 是基础规范检查，不替代行为、安全、持久化、性能和架构边界审查。请查看页面：https://go.dev/wiki/CodeReviewComments

## 审查维度

按相关性显式检查以下维度。

### 行为与契约

- 代码是否实现了文档、接口和调用方预期的语义？
- 操作名、返回结构、状态码、错误语义是否一致？
- 已合入、已发布、已有外部调用方依赖或已产生持久化数据的行为，是否保留了必要的兼容性和迁移路径？

### 代码有效性

- 新增逻辑是否解决了当前真实存在的问题？
- 兼容分支、fallback、feature flag、旧路径保留是否有明确对象，包括已发布版本、外部调用方、线上数据或灰度流量？
- 未合入、未发布、未形成外部依赖的代码修复，是否可以直接收敛到正确实现？
- 是否存在为了兼容未生效历史状态而引入的重复路径、死分支、配置噪音或长期维护负担？

### 安全与权限

- 身份是否只来自可信认证或可信入口？
- 租户、用户、角色、资源、对象级权限等访问边界是否在每个入口都生效？
- 查询、列表、导出、下载、批处理、派生数据等非主流程入口是否遵守一致的访问规则？

### 持久化与一致性

- 状态变更和外部副作用的提交顺序是否可恢复？
- 失败路径是否会留下不可达资源、悬空引用、重复副作用或过期状态？
- 并发写是否在合适粒度上处理？
- 测试替身和真实实现的语义是否足够一致，使测试有意义？

### 性能与资源

- 代码是否把无界数据加载进内存？
- 大输入、批量数据、分页、流式处理、超时是否被明确处理？
- cache 是否有边界、失效规则，并且只缓存适合缓存的数据？
- 看似局部的操作是否仍然隐藏了大范围扫描或全量加载？

### 边界与依赖

- 可复用层是否依赖稳定抽象，而不是具体基础设施或业务实现？
- 具体存储、数据库、外部服务等依赖组装是否放在启动、配置或 factory 层？
- 业务特定概念是否被隔离在业务层，而不是泄漏到通用基础组件？

### 测试

- 测试是否覆盖真实实现或关键集成路径，而不仅是 mock/fake/in-memory 替身？
- 失败路径、并发或陈旧写、权限拒绝、大输入、迁移或兼容 fallback 是否被覆盖？
- 测试是在断言 public behavior，还是绕过 public method 使用 test-only helper？
- 修复是否包含针对真实失败路径的回归测试？

### 可维护性

- 代码是否围绕稳定领域能力组织，而不是堆进 generic helper？
- 审查者是否能分别定位主流程和底层机制？
- 抽象是否真的降低复杂度，而不是只移动代码？
- 文件大小是否已经影响 diff 局部性、人类审查或 LLM 导航？

## 变更价值判断

不是每个问题都应该立刻修。

使用这个判断规则：

- 影响生产行为、安全、持久化、迁移、默认用户路径的问题，当前修。
- 主要是架构整洁性，并且后续计划工作会自然触达同一区域的问题，可以暂缓。
- 暂缓真实技术债时，要说明触发条件和后续处理时机。

表达取舍时，用风险、成本和时机说明。不要把暂缓的问题描述成已经解决。

## 输出结构

代码审查回复应先列出审查项和审查结果，再汇总有问题的意见。

先给审查项结果表或列表，覆盖本次实际检查过的维度。每个审查项都要有结果，即使没有问题也要写明。

推荐结果值：

- `通过`：已核查，未发现问题。
- `有问题`：已核查，发现需要处理的问题。
- `未覆盖`：本次没有足够证据完成审查，说明缺少什么证据。
- `不适用`：该审查项和本次改动无关。

审查项可以包括：行为契约、代码有效性、安全权限、状态一致性、性能资源、依赖边界、测试覆盖、语言基础规范、可维护性等。

然后汇总有问题的 finding。每条 finding 包含：

- 严重程度。
- 具体标题。
- 文件和行号证据。
- 影响。
- 建议修法或需要决策的点。

最后再给：

- 影响结论的开放问题或假设。
- 已执行的验证。
- 剩余风险或暂缓债务。

如果没有发现实质问题，仍然要保留审查项结果，并明确说明没有需要汇总的 finding。

## 修复后验证

修复后不要停在测试变绿，也不要只验证上一轮指出的问题。复审应重新覆盖完整审查面，并确认修复没有引入新的全局回归。

还要验证：

- 旧代码路径或旧依赖已经消失。
- 新行为被相关测试覆盖。
- 不再需要的兼容分支、fallback、feature flag、临时配置已经移除或明确标注了删除条件。
- 修复没有破坏其他入口、核心用户路径、权限边界、状态一致性、性能资源边界或依赖方向。
- 生产实现与测试替身实现了同一契约。
- 静态检查和格式化通过。
- 没有 debug 输出、临时命名或半成品重构残留。

重构后应使用 targeted grep 检查已知失败模式和依赖残留。
